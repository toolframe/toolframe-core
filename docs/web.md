# Web applications and presentation mounts

Core routes complete HTML applications through the independently installed Web
provider. Business plugins declare SDK `web.app` resources and keep their domain
logic in ordinary services. Web works without Streamlit or a process provider.
The Web cohort is independent of business workers and the Dashboard UI cohort.

## Create a notes application

Use a Core 0.8 executable or `toolframe-core` Python entry point. Install the CLI
and select the published Web authoring package explicitly:

```sh
uv tool install toolframe==0.8.3
toolframe --home ./notes-app init
toolframe --home ./notes-app plugin new notes --from pypi:toolframe-web==0.1.0 --template toolframe-web/notes
toolframe --home ./notes-app web prepare ./notes-app/plugins/notes
```

Preparation prints a wheel path and SHA-256. It captures source, prepares explicit
browser assets in a separate staging tree and builds that wheel. The source tree
stays editable. First preparation can download pinned htmx/Tailwind artifacts;
`--offline` uses previously verified cached inputs. No Node/npm installation is
required. The default `plugin new` template is provider-free basic. Web Notes is supplied
by the optional Web wheel; acquiring it does not enable its runtime provider.
See [distribution authoring](authoring.md) for discovery and source selection.

Configure the initial application while it is stopped. Keep its generated
`application` section and set top-level `schema_version = 2`:

```toml
[plugins.sql-sqlite]
source = "pypi:toolframe-sql-sqlite==0.4.1"
enabled = true

[plugins.web]
source = "pypi:toolframe-web==0.1.0"
enabled = true

[plugins.notes]
source = "wheel:plugins/notes/build/web/toolframe_notes-0.1.0-py3-none-any.whl"
enabled = true

[gateway]
landing_target = "web.notes.main"

[gateway.mounts."web.notes.main"]
prefix = "/"
```

Start with `toolframe --home ./notes-app serve`. The app serves complete forms,
htmx fragments and JSON at its public URL. The Notes starter uses managed SQL,
read/write scopes, idempotent creates and optimistic row revisions. The Web
provider supplies autoescaped templates, forms and sealed assets; it does not own
business data.

The Web starter uses pages-first Feature-Sliced Design: `web/app` owns routes,
entrypoints and global styles, while `web/pages/notes` owns UI/templates, view
state and its service adapter. Python `__init__.py` and ESM `index.js` expose the
page's public API. Page slices stay independent and depend only on lower layers;
add shared/features/entities only for actual reuse. Browser inputs stay beside
their owner, while the explicit manifest controls staging/wheel output paths.
This structure adds no Node/npm or frontend build dependency. Business schemas
remain in `contracts.py`; transactions, idempotency and row rules stay in the
business service. The starter shares notes among authorized callers and does not
implement per-person isolation or automatically publish MCP tools. The installed
authoring skill describes optional private MCP publication and further layout
guidance. Existing source is never regenerated by a binary/skill update.

For an already running application, use normal `plugin add`, `validate`, `enable`,
`update` and `reload` operations. A configuration edit takes effect through
`toolframe --home APP apply`. A source install also performs Web preparation;
installing a prepared wheel never compiles browser assets. Keep current policy
and data when extending an application.

## Select the root explicitly

Schema version 1 retains the existing Dashboard-at-root behavior. Version 2 has
no automatically selected presentation root. With a Web root and Dashboard:

```toml
[gateway.mounts]
"web.notes.main" = { prefix = "/" }
"provider.dashboard" = { prefix = "/console" }
```

Reverse these to place Dashboard at `/` and Web at `/notes`. App-relative URL
helpers include the mount prefix; Web `/notes` redirects GET/HEAD to `/notes/`.
Dashboard's base URL is passed during activation, including its assets and
WebSocket endpoint. A non-root Dashboard requires `gateway-endpoints-v1` support.

Mounts match complete segments. Duplicate roots, reserved namespaces, unknown
targets and Web route declarations shadowed by nested mounts fail validation.
A disabled or unavailable selected app keeps its mount and returns 503; it does
not hand root to a different app. With no root mount, `/` lists available,
authorized entrances. `landing_target` selects the default post-login/logout URL.
Validated same-origin `return_to` can return a sign-in to the original app.

Core reserves `/_toolframe`, `/healthz`, `/.well-known`, `/oauth`, `/mcp`,
`/llms.txt` and `/llms`. Protocol mounts cannot be relocated by this version;
changing the presentation root preserves OAuth issuer, callback and MCP resource
semantics. Unknown reserved Core routes are never an app's SPA fallback.

## Access, updates and failure

The existing browser access policy applies to Web. Select protected access and
`failure_mode="closed"` for confidential applications; an app can additionally
require authentication. Resource, route and business method scopes are checked
separately. GET/HEAD cannot invoke mutating methods. Browser credentials never
reach the Web worker; Core issues a request-bound opaque reference and rechecks
permissions for service calls. Same-origin apps are trusted code, not sandboxes.
The provider authorizes the selected route before body/form decoding; this first
phase grants no service-call permission. Complete admission then verifies proofs
and rechecks access. Displayed scopes use that same principal, including when an
authenticated resource overrides global public business access.

Unsafe requests require Core-issued CSRF and Web revision proofs. A stale page
receives 409, so reload the document before another mutation. Full HTML navigation
can redirect to login; fragment/JSON requests retain an HTTP error. Templates
escape text and the default CSP permits sealed same-origin assets without inline
script execution. Public assets are an explicit app-level choice; inherited
assets authenticate before conditional 304 responses.

Publication validates templates, routes, asset hashes and dependencies before
selection. Failed preparation leaves the old app active. A successful update
changes the page revision. The immediately previous asset set remains available
for ten minutes while its owner is enabled, under the current access policy.
HTML/fragments are private and not cached; old pages must not mix new fragments
with old assets. A restart serves retained wheels; the previous-set grace is
not a promise across a Core restart.

Requests, forms, uploads, synchronous handlers and responses have bounded limits.
The default Core limits are 8 MiB request bodies, 30 seconds and 64 in-flight
requests. The provider allows eight synchronous handlers, eight uploaded files,
128 ordinary fields for either form encoding, 256-byte field names, 64 KiB field
values, 4 MiB per upload, and 8 MiB rendered responses. A disconnected or
timed-out browser does not roll back a domain call already admitted by Core.
Use service-level idempotency keys for retried mutations.

Generic ASGI mounts, WebSocket/SSE apps and streaming responses are outside Web
contract v1. Streamlit's existing WebSocket support remains available. Browser
asset preparation supports explicit local files and pinned HTTPS inputs; Tailwind
standalone supports macOS and glibc Linux on ARM64/x86-64. External OIDC and each
platform must be verified in its own deployment.

Back up a stopped application's configuration, private state, retained artifacts
and data through the [maintenance interface](offline-maintenance.md). Restoring
those sealed wheels does not need author source, Tailwind or a browser CDN;
rebuilding Python environments still needs cached or downloadable dependencies.
Web cohort recovery requires Toolframe Backup 0.2.1 or newer, which records and
reconstructs Web environments alongside backend and Dashboard environments.
